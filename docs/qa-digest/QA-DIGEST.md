## SECTION 1 — Application Overview

**Purpose:** A fee/admissions management back-office system for a coaching/tuition institute chain
("Shri Ji Complete Educational Solutions" — name appears in receipt headers, page footer, and hero
copy). It replaces manual/paper admission registers and fee collection ledgers with a digital
workflow: enroll a student (admission), collect the initial deposit, track subsequent installment
payments against that admission, generate GST-compliant receipts, and report on collections.

**Business Goal:** Give institute staff a fast, centre-scoped, session-scoped (academic-year-scoped)
tool to register admissions, collect fees in installments, print/download tax-compliant receipts, chase
overdue payers via WhatsApp reminders, and give management (admin) dashboards, GST/fee reports, and
user/master-data administration.

**Application Type:** Single-Page Application (SPA), authenticated back-office / internal tool — not a
public-facing product. No self-service signup; access is invite-only.

**Primary Users:**
- **Admin** — institute owner/manager. Full access: dashboards with institute-wide KPIs, reports, user
  management, settings (institute details, master data, notifications).
- **Staff (Cashier)** — front-desk/collections staff. Can record admissions, collect installments, view
  their own collections on a scoped dashboard, but cannot access Users or Reports pages, and cannot see
  Institute Details or Notification settings.

**Main Features:**
1. Student Admissions (create, edit, cancel, bulk-upload via Excel)
2. Fee Installments (record payments, view transaction history, bulk-upload, overdue tracking, WhatsApp reminders)
3. Receipts (auto-numbered, GST-split, PDF download/print)
4. Dashboards (role-specific — Admin sees institute-wide charts; Staff sees "my collections")
5. Reports (Fee Report + GST Report, CSV export) — **admin only**
6. Global student search (typeahead by roll no/name)
7. Settings (profile, password, institute details, banks/courses/centres master data, notification toggles)
8. User management (invite-based, roles, activate/deactivate) — **admin only**
9. Multi-centre + multi-academic-session scoping (every screen is implicitly filtered by the centre and
   session selected in the Topbar)
10. In-app notification bell (new admission / new installment / reminder events)

**Business Domain:** EdTech / Education Administration — Fee & Admissions Management (Indian market,
per GST/CGST-SGST split, `en-IN` formatting, and INR currency).

Standard response envelope: `{ data... }` for single/paginated resources, flat objects for auth
endpoints, and `{ error: { code, message } }` for all error bodies.

### 2.4 Database

### 2.5 External Integrations
- **WhatsApp** — installment payment reminders (`POST /installments/remind`); confirmed via dialog copy ("This will send a WhatsApp reminder..."), not via any visible WhatsApp SDK/webhook in the FE (send is entirely server-side).
- **Presumed email** — invite emails (`POST /users`), password-reset emails (`POST /auth/forgot-password`), email-verification codes (`POST /auth/resend-verification`) — all backend-driven, no FE email client code.
- **Presumed S3 (production)** — receipt PDFs use a presigned URL pattern in prod (`pdfUrl` expires ~1h); in dev, PDFs are served from the same backend origin under `/files`.
- **Google Fonts** — `Inter` font family loaded via `index.html`.
- **ngrok** (dev only, currently configured in `vite.config.ts`) — tunnels the dev proxy to a remote backend; not a production integration.

### 2.6 Authentication
JWT access token (~15 min lifetime) held **in-memory only** (module variable in `src/lib/axios.ts`,
never written to storage) + an httpOnly, server-rotated refresh cookie the browser sends automatically.
Silent refresh: proactive every 14 minutes, reactive on any 401 (queued so concurrent 401s share one
refresh call). Refresh failure → hard `window.location.href = '/login'` (full page reload, not SPA nav).

### 2.7 Authorization
Two roles: `admin`, `staff` (`src/constants/roles.ts`). Enforcement is **entirely client-side** at the
UI layer (`RoleRoute` component gates `/users` and `/reports`; `Topbar` nav filtering hides the links
for staff). **No backend authorization behavior is visible from this repo** — Section 15 (Security)
flags this as a mandatory test point: confirm the backend independently rejects a `staff` JWT calling
admin-only endpoints directly.

## SECTION 6 — Complete User Journey

### 6.1 Admin — Happy Path
1. Navigate to `/login` → select centre → enter email/password → Sign In.
2. Redirected to `/dashboard` → sees institute-wide KPIs, class-wise collection chart, payment-methods breakdown, recent admissions/installments tables.
3. Navigates to Admissions → Add New Admission → fills form → submits → admission created, redirected to list.
4. Prints receipt from the list (Print icon) → PDF blob downloads.
5. Navigates to Installments → Add New Installment → types Admission Number → auto-lookup fills student/course/fee fields → enters payment amount/method → submits.
6. Navigates to Reports → Fee Report tab → searches by roll number → exports CSV.
7. Navigates to Settings → adds a new Course to master data → toast "Added successfully".
8. Navigates to Users → invites a new staff member → toast "Invite sent to {email}...".
9. Logs out via Topbar avatar menu.

### 6.2 Staff — Happy Path
1. Login (same as above, sees only their assigned nav items — no Users/Reports).
2. Dashboard shows "My Students" / "Pending Fees" / "Today's Collection" KPIs and a "Recent Collections by You" table only (no charts).
3. Records an admission or installment (identical forms to admin).
4. Cannot navigate to `/users` or `/reports` (redirected silently to `/dashboard` if attempted via URL bar).

### 6.3 Alternative Paths
- Admin switches Centre or Session mid-session via Topbar chips → entire TanStack Query cache is wiped (`queryClient.clear()`), ETag store cleared, socket re-scoped — every screen refetches from scratch.
- Staff uses Global Search to jump straight to a student's roll number (though the deep-link filter itself doesn't apply — see EDGE-041).
- Admin uses "Record New Installment" directly from an Admissions/Installments row menu (admission number pre-locked).

### 6.4 Negative Paths
- Wrong password on login → inline error alert (message depends on backend).
- Empty required fields on any form → inline Zod errors, submit blocked.
- Admission form: `fees > finalFees` → cross-field error "Fees paid cannot exceed final fees".
- Reset password with missing/garbled `?token=` → dedicated "Invalid reset link" screen (no form shown at all).

### 6.5 Permission Path
- Staff types `/users` or `/reports` directly into the address bar → silently redirected to `/dashboard`, **zero toast/message explaining why** (EDGE-089).
- An admin's role is downgraded to staff by another admin while the first admin is mid-session → their live session does not lose access until token refresh/reload (EDGE-090).

### 6.6 Error Path
- Backend 500 on any list query → for Dashboard, Reports (Fee/GST), and several others, the UI shows the **same "no data" empty state as a genuine empty result** — no distinct error banner (EDGE-050, EDGE-051, EDGE-118).
- Network failure mid-mutation (create admission/installment) → inline root-level Alert with best-effort message extraction; the idempotency key allows a **safe retry** on the exact same form mount.

### 6.7 Session Timeout Path
- Access token expires after ~15 min; if the 14-min proactive refresh succeeds, invisible to the user.
- If proactive refresh silently fails, nothing happens until the next real API call 401s → interceptor attempts one more refresh → if that also fails, hard redirect to `/login` via `window.location.href` (full reload, **any unsaved form input is lost with zero warning** — EDGE-006).

### 6.8 Browser Refresh Path
- All in-memory state (access token, Zustand stores) is lost.
- `App.tsx` bootstrap silently attempts `POST /auth/refresh` using the httpOnly cookie; on success the user lands back where they were (React Router preserves the URL across a hard refresh since it's a fresh page load of the same path) after two sequential loading-spinner gates (`bootstrapped` → `shellReady`).
- Editing an admission and hard-refreshing `/admissions/:id/edit` **correctly re-fetches the record** (contradicts the stale architecture doc — see §22). Editing an *installment* and refreshing does **not** work the same way (see EDGE-070).

### 6.9 Back Button Path
- After logout via the in-app button (SPA navigation), pressing Back re-renders a protected route component, but `ProtectedRoute` immediately re-redirects to `/login` since `isAuthenticated` is now false — safe.
- After a **refresh-failure-triggered** hard redirect (`window.location.href`), the SPA's client-side history is wiped; Back goes to whatever page was open *before* the app itself, not an in-app route.

## SECTION 7 — Feature Workflow

### 7.1 Admission Creation
- **Start event:** User clicks "Add New Admission" → fills form → clicks "Submit Admission".
- **Business logic:** Client generates a `crypto.randomUUID()` idempotency key once per page mount (survives repeated submit attempts on the same mount, regenerates on remount). Cross-field rule: `fees ≤ finalFees`. No `status` is set by the client — left to backend default.
- **API call:** `POST /admissions` with header `Idempotency-Key: <uuid>`, body = `CreateAdmissionDto`.
- **DB changes (inferred):** New admission record created; presumably a receipt record is generated server-side (the list's `receiptId` field becomes populated at some point, enabling the Print action) — **not directly observable from FE**, flagged as an assumption.
- **Notifications:** Success toast "Admission created successfully". (No auto-print/auto-open-receipt happens — despite ARCHITECTURE.md's claim; see §22.) Backend presumably fires a `new_admission` in-app notification (consistent with the Topbar bell's icon-type mapping) and possibly the `dashboard:changed`/`admissions:changed` socket events (only `dashboard:changed` is confirmed wired client-side).
- **Validation:** See Section 9.
- **Completion criteria:** Redirect to `/admissions` list; new row visible after the `admissions.all` query-key invalidation.

### 7.2 Admission Edit
- **Start event:** Click Edit icon on an Admissions row → navigates to `/admissions/:id/edit`.
- **Business logic:** `AddAdmissionPage` fetches the record fresh via `GET /admissions/:id` (not via router state). Builds a **diff-only PATCH** — only changed fields are sent, except `depositDate` which is always sent if truthy regardless of change. Inactive-course values are preserved via a disabled "(inactive)" option so the field never blanks out.

- **API calls:** `GET /reports/fees`, `GET /reports/fees/export` (blob), `GET /reports/gst`, `GET /reports/gst/export` (blob).

### 7.11 Settings — Master Data (Banks/Courses/Centres)

- **Completion criteria:** Toast "Added successfully" / list count updates; consuming dropdowns elsewhere in the app reflect the change without a full reload.

### 7.12 User Invitation (admin only)

- **Notifications:** Toast `Invite sent to {email}. They'll set their own password.`
- **Completion criteria:** New row appears with status "Pending"; "Resend invite" action becomes available on that row until activated.

## SECTION 11 — State Management

### 11.1 Server State (TanStack Query)
- Global defaults: `staleTime` 5 min, `gcTime` 10 min, `retry` ≤2 (skips 401/403/404), `refetchOnWindowFocus: false` globally — **but individual queries override this** (e.g., Dashboard sets `refetchOnWindowFocus: true`).
- Per-feature `staleTime` overrides: Dashboard 60s, Admissions/Installments/Users 30s, Reports (Fee/GST) 30s.
- Query keys centralized in `constants/queryKeys.ts` — **exceptions found:** Students list, `useInstallmentTransactions`, and Reports all use inline literal key arrays instead of the factory (inconsistent, complicates cache debugging).
- `queryClient.ts` global `mutations.onError` only logs — never shows a toast; every mutation is individually responsible for user feedback.

### 11.2 Client State (Zustand)
| Store | Persisted? | Holds | localStorage key |
|---|---|---|---|
| `authStore` | No | `user, isAuthenticated, bootstrapped` | — (in-memory only) |
| `uiStore` | **Yes** (`persist` middleware) | `themeMode, sidebarOpen` | `ui-store` (zustand's own JSON envelope) |
| `appShellStore` | No (manually seeded from localStorage at module load) | `centres, sessions, centreId, sessionId, unreadCount, shellReady` | `centreId`, `sessionId` (raw strings, written directly, not via the store's persist) |
| `useSnackbar` (feedback) | No | `open, message, severity` | — |

### 11.3 Access Token
In-memory module variable only (`src/lib/axios.ts`). Never touches any storage. Refresh token is an
httpOnly cookie the FE never reads.

### 11.4 Dead/Unused Storage Code
`src/utils/storage.ts` defines a generic `app_`-prefixed localStorage wrapper (`STORAGE_KEYS.AUTH_TOKENS`,
`THEME_MODE`, `USER`) that is **never imported anywhere in the codebase** — confirmed dead scaffold
code implying an abandoned earlier storage strategy.

### 11.5 Refresh / Cache Invalidation Triggers
- Mutation `onSuccess` → `queryClient.invalidateQueries` (targeted per-feature `.all` key) — the primary invalidation mechanism for Admissions, Installments, Users, Master Data.
- Centre/Session switch (Topbar) → `queryClient.clear()` (nukes **everything**, not scoped) + `clearEtagStore()` + `setSocketScope()`.
- Socket `dashboard:changed` event (self-skip via `actorId`) → targeted dashboard invalidation. **This is the only module with confirmed realtime wiring** — Admissions/Installments/Users/Reports have none (rely solely on staleTime + manual invalidation).
- ETag-based conditional-GET polling (8s interval) is the documented fallback when the socket is disconnected — confirmed implemented generically in `lib/conditionalGet.ts` and wired for Dashboard; **not confirmed wired for any other module** in the reviewed files.

### 11.6 Persistence / Local Storage / Cookies Summary
| Storage | Key | Content | Sensitive |
|---|---|---|---|
| localStorage | `ui-store` | theme mode, sidebar flag (JSON) | No |
| localStorage | `centreId` | selected centre id (raw string) | Low (identifier, but used as a trust boundary — see Security §15) |
| localStorage | `sessionId` | selected academic session id (raw string) | Low (same caveat) |
| Cookie (httpOnly) | refresh token (name/path not visible to FE) | rotating refresh token | **Yes — must verify `Secure`/`SameSite` flags server-side** |
| In-memory only | access token | JWT | Yes |

## SECTION 17 — Risks

### 17.1 Business Risks
- **Non-functional Admissions bulk upload** (EDGE-021/022) — if staff believe they've successfully bulk-imported admissions via that dialog, they may proceed as if data exists when it does not, risking under-reported enrollment/collections until discovered.
- **Unwired installment cancel/verify** — no supported workflow exists to reverse a bad installment entry or move a pending-verification payment to paid, which may force error-prone workarounds (e.g., re-entering corrected data without voiding the original) unless this is intentionally deferred to a backend-only/manual process.
- **Ambiguous error-vs-empty states** (Dashboard, Reports) could mask real outages as "there's just no data," delaying incident detection by institute staff/admins.
- **Financial correctness gaps**: no upper-bound or overpayment guard on installment "Fees" entry (EDGE-065) could let staff record clearly-wrong amounts without a client-side sanity check.

### 17.2 Technical Risks
- **Client-side-only role/scope enforcement** — a real security exposure if the backend does not independently enforce role (`admin`-only endpoints) and centre/session scoping. This is the single highest-priority technical risk in this review and must be verified against the live API before go-live.
- **`queryClient.clear()` on every centre/session switch** wipes the *entire* app cache, not just scoped data — likely fine functionally but a performance/perceived-responsiveness risk on slower connections (every screen refetches everything).
- **Two independent, manually-synced caches for banks/courses** (TanStack Query in Settings + a hand-rolled module cache in Admission/Installment forms) — a future missed `invalidateDropdown()` call would silently reintroduce stale dropdown data.
- **GST Report fetches all months in one call, paginating client-side** — will degrade over a multi-year institute lifetime.
- **Dead/unreachable code paths** (installment cancel/verify/edit, `studentLookup`, `setStatus`, `getOne` for installments) increase maintenance risk and make it easy for future developers to assume a feature works when it's actually orphaned.

### 17.3 Testing Risks
- **No live environment/credentials available at digest-generation time** — every claim in this document about actual runtime behavior (as opposed to code structure) needs live verification before being trusted as ground truth.
- **Backend is entirely out of scope of this repo** — API contract details (exact error codes, whether centre/session scoping is truly enforced, whether master-data deletes are truly soft) are inferred from the frontend only and could be wrong.
- **`ARCHITECTURE.md` contains confirmed-stale claims** (edit-via-location.state, auto-print-on-create, admissions date-range filters, `host:true` dev server binding) — testers who rely on that doc instead of this digest will write tests against features that don't exist.

### 17.4 Regression Risks
- Any change to the shared `errMsg`/`useApiError` error-extraction logic risks breaking multiple duplicated implementations across the codebase simultaneously (at least two near-identical `errMsg` helpers were found for Admissions alone).
- Any change to `useDropdown`'s module-level cache or its `invalidateDropdown` call sites risks silently reintroducing stale course/bank data in Admission/Installment forms.
- The Notifications-settings "always send both keys" constraint (BR-14) is a landmine for any future refactor that "simplifies" the toggle handler to send only the changed key.

## SECTION 20 — Automation Readiness

### 20.1 Stable Locators
- The app has **no `data-testid` attributes anywhere** in the reviewed source. Automation must currently rely on:
  1. `getByRole` + accessible name (buttons/labels mostly have clear text — "Sign In", "Add New Admission", "Submit Admission", etc.)
  2. `getByLabel`/`getByPlaceholderText` for form fields (labels and placeholders are consistently present and are quoted verbatim throughout this digest for exactly this purpose)
  3. Exact, stable toast/message text (catalogued in Section 12) — good regression-assertion targets since they're hardcoded strings, not derived dynamically (aside from interpolated names/counts)
- **Recommendation:** before investing heavily in automation, request `data-testid` attributes on primary interactive elements (submit buttons, table rows, dialog confirm/cancel buttons) — MUI's generated class names (`css-1a2b3c`-style) are explicitly unstable and must never be used as selectors per this repo's own QA-ARCHITECTURE.md guidance.

### 20.2 Dynamic / Risky Components
- MUI `Select` dropdowns (Course, Bank, Payment Method, Role, Status filters) — require `getByRole('combobox')` + `getByRole('option', {name})` patterns, not raw `<select>` assumptions.
- Debounced search inputs (Global Search 250ms, list-page searches 300ms) — tests must wait for the debounce window before asserting on results, not click-and-immediately-assert.
- Toast/snackbar auto-hides after 4 seconds — assert on the toast **immediately** after the triggering action, don't rely on it still being visible moments later.
- Chart components (Recharts, Admin dashboard) — avoid asserting on rendered SVG paths; assert on the underlying data-driven text (KPI card values, "No data yet" fallback) instead.
- Bulk-upload dialogs — the Admissions one is non-functional; do not write a "successful bulk upload" test for Admissions until the feature is actually wired (write a test asserting the current *lack* of a network call instead, if regression-tracking the defect is desired).
- Idempotency-key-generated forms (Add Admission, Add Installment) — remounting the component (navigate away/back) changes the key; tests relying on retry-safety must stay on the same mount.

### 20.3 API Mocking
- Recommended for: Dashboard (chart/empty-state variations), Reports (large datasets, error states), realtime socket events (hard to reproduce live) — use Playwright's `route.fulfill()`/`page.route()` to simulate `dashboard:changed` preconditions, empty GST months, and 500 responses to specifically test the "error looks like empty" gaps flagged throughout Section 16.
- Auth flows (401→refresh→retry queue) are excellent candidates for API mocking since reproducing exact-timing race conditions (concurrent 401s) against a real backend is unreliable.

### 20.4 Reusable Components (good automation leverage points)
- `ConfirmDialog` — one component used for every destructive confirmation (cancel admission, delete user, resend invite, remove master-data item) — a single well-tested Page Object for this dialog covers many flows.
- `StatusBadge`, `PageHeader`, pagination footer pattern — repeated verbatim across Admissions/Installments/Users/Fee Report; a shared Page Object/helper for "the standard paginated table" will cover most list screens with minimal duplication.
- `GlobalSnackbar` — single toast mechanism; one assertion helper (`expectToast(message, severity)`) covers the majority of success/error verifications in Section 12.

### 20.5 Recommended Playwright Strategy
- ~~Use `storageState` to persist an authenticated session per role (admin/staff) and reuse across test files — avoids re-running the full login flow for every test.~~ **CORRECTED 2026-07-08 (live-confirmed, supersedes the original recommendation above):** the refresh token is **single-use/rotating**. A `storageState` snapshot captured once can be consumed by exactly **one** additional browser context — reusing that same original snapshot a second time (even sequentially, even within a single worker) fails and redirects to `/login`, because the first consumer's bootstrap `POST /auth/refresh` call already rotated/invalidated it server-side. Proven directly: two fresh contexts built from one captured snapshot — the first succeeds, the second deterministically fails. **A single shared `storageState` file cannot safely back more than one test.** The corrected approach used in `Shriji-testing/utils/fixtures/auth.fixtures.ts`: every test that needs an authenticated role performs its own fresh real UI login via a per-test fixture. This costs a few extra seconds per test but is the only reliably correct option against this backend.
- Given the **entire access token lives in memory** (not localStorage/cookies), `storageState` will only capture the httpOnly refresh cookie — verify Playwright's `storageState` correctly persists httpOnly cookies (it does) and that a fresh page load correctly re-bootstraps the in-memory access token via `/auth/refresh` before proceeding with assertions (add a wait for the post-bootstrap "shellReady" signal — e.g., wait for the Topbar to render — rather than a fixed sleep).
- Given `queryClient.clear()` fires on centre/session switch, avoid interleaving unrelated assertions across a switch action within the same test — treat it as a hard reset point.
- Given no `data-testid`s exist, prefer `getByRole`/`getByLabel` extensively (as this digest's Section 9/16 field/message catalog already documents exact accessible names and copy to select against).
